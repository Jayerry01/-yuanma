# 《流星蝴蝶剑.net》(Meteor.exe 2002) PE 架构与内存全景逆向分析

## 一、 二进制基本指标 (PE Specification)

- **目标二进制**: `C:\Program Files (x86)\Meteor\Meteor.exe`
- **文件体积**: 1,945,600 字节 (1.86 MiB / 1.95 MB)
- **SHA-256 哈希**: `baebb6d59e6da61e03660c57c31f842f8a3ec157f07d1e2f9bf8d78373a58619`
- **MD5 哈希**: `cf2aa5c21a0a687afacc5e5c0876c543`
- **架构**: x86 32-bit Little-Endian (PE32)
- **基地址 (ImageBase)**: `0x00400000` (固定装载基址，无 ASLR / DEP 随机化保护)
- **编译器/链接器**: Microsoft Visual C++ 6.0 / Visual Studio 98 SP5
- **调用约定**: 
  - C++ 类成员函数一律采用 `__thiscall` (ECX 传递 `this` 指针，被调用者栈平衡)
  - 导出/全局 API 函数采用 `__cdecl` 或 `__stdcall`

**§三 口径（2026-10-27 逐字节复核，样本 = `Meteor.exe` 1,945,600 B，md5 `cf2aa5c2…`）**

换算依据：`.text` / `.rdata` / `.data` 三节均满足 `PointerToRawData == VirtualAddress`（§二），故这三节内 `file = VA − 0x00400000`；`.data1`（Raw `0x1D6000` vs RVA `0x3F3000`）与 `.rsrc`（Raw `0x1D7000` vs RVA `0x3F4000`）**不满足**，不得套用。
> ⚠️ 本行初稿（同轮 commit `6a84dc6`）误写"`.data` 不满足"，与 §二 表自证矛盾，现按复算修正；§三 表中地址点全部落在 `.rdata`（`0x005A8000`..`0x005C3E0E`），修正只影响适用域表述，**不影响任何一条已记录的读数**。
> `.data` 的附加限制：其 VSize `0x22EEF4` 远大于 RawSize `0x12000`，只有 `0x005C4000 ≤ VA < 0x005D6000` 这段在文件里有字节；再往上是 BSS，套该式会读到 `.data1`/`.rsrc` 的原始数据，是**静默错值**而非报错。
以下每条都是按该式直读 4 字节得到的，不是转储文本。

- **槽号规则（本节及全系列文档一律遵守）**：`槽号 = 调用点位移 / 4`，**基址取对象首字被实际写入的那个 vfptr 值**。同一段连续指针数组上可以并存多个地址点，所以"第 N 槽"不写锚点就不是事实——旧版本此节只写"150 个方法指针 / 角色控制器的虚函数入口表"即属藏锚。
- **游程算术自检**（比逐字节再读一遍便宜，但**只是必要条件**）：落在 `0x005AA658` 那 150 游程内的任意地址 `A`，其 code-ptr 游程必须 = `150 − (A − 0x005AA658)/4`。实测四个点全中：

  | 地址点 | 偏移槽数 | 预测游程 | 实测游程 | 槽 0 | 位移 0 安装点 |
  | :--- | :--- | :--- | :--- | :--- | :--- |
  | `0x005AA658` | 0 | 150 | 150 | `0x004C5A60` | 6（`0x4C5A40`/`0x4C61BD`/`0x4C7023`/`0x4C7943`/`0x502AFD`/`0x502B3E`）+ 1 栈槽 `0x4C4FCB` |
  | `0x005AA660` | 2 | 148 | 148 | `0x004C8880` | 2（`0x4C8854`/`0x4C88C1`） |
  | `0x005AA6A8` | 20 | 130 | 130 | `0x004CAD80`（deleting destructor） | 2（`0x4CAD53`/`0x4CADC2`） |
  | `0x005AA88C` | 141 | 9 | 9 | `0x004D11C0` | 2（`0x4CAD41`/`0x4D0F82`） |

  该式能否掉"随便挑一个数组中途当表基"的假锚点（预测游程对不上就是读错了），**但不能证明 `A` 是表头**：`0x005AA660`、`0x005AA6A8`、`0x005AA88C` 三行同时满足该式，且各自都有位移 0 安装点 ⇒ 它们是**不同类的表**紧排在同一段里；反之若某点满足该式而**没有**位移 0 安装点，才只是数组中途。
- **表头判定的唯一硬证据 = 安装点普查**：把候选表地址按小端打包成 4 字节，在 `.text`（原始窗口 `0x1000..0x1A8000`）里全搜 imm32，逐条反汇编确认写入目标是**对象位移 0**（`c7 0x`/`c7 4x 00` 形态）还是别处（栈槽、`+4`、参数）。命令实测一条即可复现：
  `python -c "import struct,re;d=open('Meteor.exe','rb').read();t=d[0x1000:0x1a8000];print(len(re.findall(re.escape(struct.pack('<I',0x5AA6A8)),t)))"` → `2`。
  顺带得到一条结构结论：`0x5AA658` 有 6 个安装点而 `0x5AA660/A8/88C` 各只有 2 个 ⇒ 前者是被多处内嵌的公共成员类（`0x4C7023`、`0x4C7943` 两处还在 `add esi, 0x24` 的数组构造循环里，元素大小 0x24），后者各自只被一个 ctor + 一个 dtor 写 ⇒ 每个地址点对应**恰好一个**类。这就是"哪个类"当前能证到的边界：**类的个数与边界可证，类的名字不可证**。

- **游程边界的证明力（初稿评为"三档、float 边界强"，复算后一律降级）**：`0x005AA658`(150)、`0x005AA660`(148)、`0x005AA6A8`(130)、`0x005AA88C`(9) **四个游程的终点是同一个地址 `0x005AA8B0`**（值 `0x3BEA0EA1`，float）。一个被四个候选表基共享的终点，**无法为其中任何一张表定界**，所以"表尾紧跟常量池 ⇒ 边界强"这个判断是错的：float 边界只比 null 边界多证明"这里不再是 code 指针"，不证明"某张表到此为止"。`0x005A9068` 的终点 `0x005A9478` = `0x3ACCCCCD`（float）同理。`0x005AAB00` 的终点是 `0x00000000`——**null 在虚表里本身可以是合法槽位**（纯虚 / 空槽），故 283 只是"连续非空指针的长度"，是这几条中最弱的一条。
  ⇒ 统一结论：这些数**全部只证明"连续 code 指针到此为止"，没有一个能证明"该类有 N 个虚函数"，也不能证明"该表宽 N 槽"**。表宽的正路是安装点普查 + 槽 0 形状（如 deleting destructor 必在槽 0），游程长度至多是上界。
  同时给「游程算术自检」一条更硬的定性：因为段内任意点都止于同一边界，该式对**任何**落在段内的 `A` 都恒成立 ⇒ 它是**空洞通过**的（vacuous），只能查出抄错的地址或长度，查不出选错的锚点。初稿把它写成"能当场否掉假锚点"，此处一并更正。
- **命名来源（本节最需要标注的一条）**：`GameApp` / `PlayerController` / `SceneWorld` / `g_pGameApp` / `kJumpSpeedHigh` 这些名字**不存在于二进制里**。实测三项：
  1. 无调试信息：`IMAGE_DIRECTORY_ENTRY_DEBUG` 的 RVA = `0`、Size = `0`；全文件 `RSDS` 命中 0 次、`NB10` 命中 0 次（未链接 PDB，亦无 CODEVIEW）。
  2. 无类名字符串：1,945,600 字节全文件内 `PlayerController`、`CPlayer`、`Controller`、`GameApp`、`SceneWorld`、`MeteorUnit` 各 **0 次**命中。
  3. 无 RTTI 附着：MSVC 虚表槽 −1 应为 `CompleteObjectLocator*`（指向 `.data`）。实测八个地址点的槽 −1 逐值如下，**无一是 COL**：
     `0x005AA658` → `0x430C0000`（非 VA 值）、`0x005AA660` → `0x004C5A80`（.text 代码指针）、`0x005AA6A8` → `0x004C9910`（代码）、`0x005AA88C` → `0x004D1E90`（代码）、`0x005A9FE0` → `0`、`0x005A9FAC` → `0x004B9420`（代码）、`0x005A9068` → `0`、`0x005AAB00` → `0x3F200020`（非 VA）。
     其中三个"代码指针"正是**同一段数组里前一个槽位自身**（如 `0x004C9910` 位于 `0x005AA6A4` = `0x005AA658` 游程的第 19 槽），真实 vtable 的槽 −1 不可能是代码指针 ⇒ 这批"表基"是分析者从一段连续指针数组上取的**地址点**，不是编译器各自发射、带 COL 的独立虚表。
     全文件 `.?AV` 共 14 处（`0x005C4254`..`0x005CA6A8`，全在 `.data` 已初始化窗口内），逐个是 std 异常与 iostream 的类型描述符名（`__Named_exception@std`、`logic_error`、`length_error`、`bad_alloc`、`out_of_range`、`exception`、`ios`、`istream`、`ifstream`、`streambuf`、`filebuf`、`ostream`、`ofstream`、`type_info`），**不含任何游戏类型名**。
  ⇒ 这些符号名是**分析者按调用现场行为所起的沟通标签**，可引用、不可当证据。要主张"某地址 = 某类的第 N 个虚函数"，必须自行给出 ① 该 vfptr 的写入点字节 与 ② 调用点位移，两项缺一不成立。
- **`0x005AA6A8` 两个写入点的真实身份**（修正"两处构造点"这一说法）：
  - `0x004CAD53` `c7 06 a8 a6 5a 00` —— 位于以 `0x004CAD72 ret` 收尾、带 SEH 帧（`0x004CAD68 mov fs:[0], ecx`）的**外层对象构造函数**内；同一个函数在 `0x004CAD41` 还写了 `mov [edi], 0x005AA88C`。⇒ 外层对象内嵌**至少两个**各自带 vfptr 的成员，`0x005AA6A8` 与 `0x005AA88C` 由此同处一段数组（第四个地址点的来历）。
  - `0x004CADC2` `c7 45 00 a8 a6 5a 00` —— 位于起于 `0x004CADA0`（`push −1 / push 0x005A1994 / mov eax, fs:[0]`）的**析构函数**内，先回写自身 vfptr、再释放 `[ebp+0xE8]`、再级联析构 `[ebp+0x3D4]`。这是 MSVC 析构期的 vftable 回写，**不是构造点**；但它同样证明该值是编译器写进对象首字的真 vfptr。
  - 该类身份仍未证（见上条命名来源）。可证的是它的功能形状：槽 0 = deleting destructor `0x004CAD80`，槽 3 = 路由器 `0x004A9770`。
- **链路记录的唯一去处**：`vftable → 单例 → 子对象 → 叶子` 这条命令通道已在 `MeteorRebuild/Docs/13-combo-system.md` §1.16 完整落盘（五跳逐字节，含证伪登记与更正），**本节不复制**，只把本节表中相关地址点的锚点口径钉牢，避免他在处再写出"槽 23"式读数。
